# Personalized feed (M16)

`/feed` (+ `/feed/interests`) is the logged-in port of the mobile app's M13 Home Feed. Design doc: `StreamHub/docs/Epics/Epic Milestone 16.md`. Key facts:

- **Auth-gated, never cached**: both pages are `force-dynamic`, `robots: noindex`, and follow the `/favorites` convention (`getUser()` gate). Website auth is DORMANT but fully prepared behind a build-time flag — see the "Auth activation flag" section below. The root layout MUST stay static — never read `cookies()`/auth there (the flag is safe: a build-time constant).
- **Layering in `lib/feed/`**: `logic.ts` + `transforms.ts` are pure (unit-tested via `npm run test`, vitest); `service.ts`/`interests.ts`/`preferences.ts` take a `SupabaseClient` (server or browser — same functions serve SSR and client refresh); `loadFeed.ts` orchestrates 6 parallel error-isolated section fetches; `events.ts` is the client-only feed_events queue (30s flush, 50-cap, drop-on-failure, keepalive POST straight to PostgREST so leave-flushes survive `pagehide`).
- **Data comes from Supabase directly** (RPCs `compute_user_interest_profile`, `recommend_featured_streamers`, `fetch_feed_recent_streams`, `fetch_trending_categories`, `feed_quick_facts` + tables `stream_slots`, `stream_clips`, `stream_history`, `ai_predictions`, `user_interests`, `user_feed_preferences`, `feed_events`), NOT from the Partner API — with ONE exception since 2026-08-03: `lib/server/feed-extras.ts` (Rankings + Streamer Wiki), see below. The RPCs are granted to `authenticated` only and use `auth.uid()` — they must run under the user's session. Pass the interest profile back to `recommend_featured_streamers` verbatim (snake_case).
- **Watermark cookie** `st_feed_seen` (ISO timestamp, 30d, written client-side on leave): the server computes `since = max(now − 24h, cookie)` for "New for you"; the client keeps that value in a ref so in-session refreshes never shrink the section.
- **Constants in `lib/feed/constants.ts` mirror the app** (`useHomeFeed.ts`) — keep them in sync. Deviations from the app are deliberate and documented in the epic: `streamers.is_hidden` filtering, cancelled-slot exclusion from Up Next, no 24h interest-profile cache (recomputed per request).
- **Feed UX round (2026-07-22, website-only — no app counterpart):** invariants an agent must not accidentally undo:
  - Horizontal rails do NOT own overflow scrolling — `RailScroller` (edge fades + mouse-only chevrons) wraps them; the inner `<ul>`s are plain flex rows.
  - `UpNextMeta` deliberately renders NO reasoning teaser — `SlotCard` shows it inside the card; re-adding it reintroduces the duplicate it fixed. It carries relative start time (post-mount only), the reliability pill, and the `.ics` export (`lib/feed/ics.ts`, RFC 5545, unit-tested).
  - Dismiss events are logged DELAYED: 5s undo window (snackbar), committed early on page leave — undone dismisses must never reach `feed_events` (they'd feed the Phase-4 rank suppression).
  - Inline info cards are capped at 3 per view (`inlineInfoCandidates` in `FeedClient`); the briefing overlay keeps the full digest.
  - Anything timezone/clock-dependent (Up Next day groups, countdowns, "updated ago") renders post-mount only (`mounted` gate) — never emit it from the server.
  - Trending-game tiles navigate to internal `/game/<slug>` when `gameHubSlugs` (server-resolved in `feed/page.tsx` via ISR-cached `listGames`, degrades to `{}`) has the game; fallbacks: chip filter → Twitch directory.
  - `toPublicStreamSlot` maps `viewer_count` only for live slots with a <25min-fresh sample (partner-API contract) — the live rail's "watching" badge depends on it.
  - Lightbox playlist nav (prev/next + arrow keys) walks the source rail's embeddable clips; NO autoplay-next (the Twitch embed exposes no reliable ended signal without their player JS API).
- **Feed expansion round (2026-08-03, website-only — the app keeps Discover):** section order is now Live → Up Next → New for you → Highlights → New videos → trending rail → **Rankings** → **Your stats** → info cards → Show-more tail → **Streamer Wiki**. Invariants:
  - **Discover is GONE, the Streamer Wiki replaced it.** `DiscoverCard`, `diversityPass`, `applyDismissSuppression`, `reorderDiscover`, `buildDiscoverReasonLabel`, `buildDiscoverStatsLine`, `fetchDiscoverStats` and the `DISCOVER_SHOWN`/`_MAX_PER_CATEGORY` constants were deleted. Three things deliberately SURVIVED: `fetchDiscoverRecommendations` (**`/onboarding` still uses it** as its pick-step fallback — do not delete with a future cleanup), `FeedItemType`'s `'discover'` member (the `feed_events.item_type` CHECK constraint still lists it and the app still emits it), and the whole interest-profile path (`FeedData.profile` drives the category chips, the announcement card's top-affinity gate and the interests-invite card).
  - **Streamer page wiki teaser is gated on `PublicStreamer.has_wiki`** (2026-08-29): `app/[locale]/streamer/[slug]/page.tsx` only calls `getStreamerWiki()` when the streamer DTO says a published profile exists (`has_wiki === false` skips it; `undefined` = older API → ask as before). Before the flag the page asked for every streamer on every render and Next cached none of the 404s (`patch-fetch.js` stores only status 200) — 10,074 Partner API calls a day for five published profiles. The flag is trigger-maintained in the backend (`streamers.has_wiki`) and `/api/revalidate` purges `/streamer/<slug>/wiki` alongside the streamer page, so a publish or takedown reaches both.
- **`lib/server/feed-extras.ts` is the ONLY Partner-API reader on this page** and lives outside `loadFeed` on purpose: the key is server-only, the data is hourly-cached, and `loadFeed` re-runs on every client refresh. Rankings therefore arrive as a FeedClient **prop**, not as FeedData — a refresh never re-fetches them. All hrefs are pre-built server-side (`toHref` = `localeHref(locale, …)`) because FeedClient carries no locale.
  - **Rankings**: one block per metric = global top 3 + up to 2 best-placed favorites + the rest behind a `<details>`. A favorite on the podium is badged there and NOT repeated below. Two sources must produce identical rows: the top-100 page per metric, and `getStreamerRankings` per favorite for anyone outside it. `pickResidualFavorites` asks for a favorite unless they appear in EVERY fetched page — membership in one metric's top 100 must not suppress the call, or that streamer silently vanishes from the other four blocks. Capped at `RESIDUAL_RANKINGS_CAP` (20). Use `rankTrend` from **`lib/streamer-rankings`** (null → no arrow), never `lib/rankings`' entry-based one, which has a `'new'` state an unbounded rank cannot justify.
  - **`fetchFavoritesWeekHistory` feeds BOTH the week leaderboard and the Monday recap** (`computeFavoritesWeekTotals`). They render next to each other, so a shared source is the only thing that keeps "66 h this week" from contradicting three rows that add up to 66. The old `fetchWeeklyActivity`/`computeWeeklyRecap` pair read `stream_slot` rows and counted ROWS as streams — both wrong next to a vod-based session union. Do not reintroduce a second source here.
  - **The section nav needs a fresh `items` identity to re-prune.** `HomeSectionNav` checks which anchors exist inside its `items` effect, so `FeedClient` passes a `useMemo`'d list keyed on `selectedCategory`; without that, chips for the sections a category filter removes survive their own sections and jump nowhere. Rankings + Your stats hide entirely under an active chip (neither is category-scoped).
  - **`HomeSectionNav` must NOT be wrapped in a sizing div** — a `position: sticky` element sticks only inside its parent, so a wrapper sized exactly to the bar makes it scroll straight away (observed here). Pass `bleedClass` instead; `/feed` uses `-mx-4 px-4` to match its `px-4` container (the homepage default is `-mx-6 px-6`). Mismatch it on the wide side and narrow viewports gain a horizontal scrollbar.
  - **Sticky stack is a px contract**: nav 61px (measured) → the category chips stick at `top-[calc(var(--header-height)+61px)]` and anchors carry `FEED_SECTION_ANCHOR_CLASS` (`lib/feed/anchors.ts`, +8.5rem). All three are LITERAL Tailwind classes — a template-interpolated arbitrary value generates no CSS at all.
  - **The Streamer Wiki is a SERVER sibling of `FeedClient`**, rendered by `page.tsx`: it takes `Map`/`Set` props and resolves its copy through `hubLexFor`, neither of which crosses a client boundary. Consequences to keep in mind: it is the one section that stays visible under a category filter, it logs no section impression (the observer only scans FeedClient's subtree), and it is the only LOCALIZED copy on an otherwise English page — accepted, the alternative was a client-side re-implementation. It excludes the viewer's own favorites (it is the discovery surface now).
  - **`SECTION_ORDER` deviates from the app**: `'discover'` → `'rankings'` + `'stats'`. Safe because `feed_events.item_id` is free text; only `event` and `item_type` are CHECK-constrained.
  - **Quick facts** (`feed_quick_facts` RPC, StreamHub migration `20260803090000`) reuse the homepage parsers, so the payload shapes must stay identical. Two deliberate differences: a much lower histogram floor (`FEED_HISTOGRAM_MIN_SESSIONS` 30 vs 200 — `parseStartHistogram` gained a `minSessions` param for exactly this) and comparative rather than superlative copy, because over ten channels "more than at any other hour" is a claim about noise. The prime-time/busiest-day values render through the homepage's `LocalPrimeTime`/`LocalBusiestDay` islands (UTC on the server, viewer frame after hydration); their label tables are built in `page.tsx` and passed down — never format them in the browser.

# New-user onboarding (2026-07-22)

`/onboarding` is the post-signup wizard (app-onboarding port): choice → import Twitch follows OR pick favorites manually → done. Same gated-page conventions as `/feed` (force-dynamic, noindex, `signInGateRedirect`, robots.txt disallow). Key facts:

- **Entry points — returning users are never redirected here**: (1) the OAuth callback sends FRESH signups (account `created_at` < 5 min, `isFreshSignup` in `lib/onboarding.ts`) to `/onboarding` — Twitch signups directly to `?step=import`; an explicit `?next` survives as the wizard's finish target and a `next` already inside `/onboarding` passes through untouched (the wizard's own "Connect Twitch" round-trip). (2) `/auth/confirm` `type=signup` success defaults to `/onboarding` (`confirmResultRedirect`). (3) The feed's `EmptyFavoritesCard` links to it. All pure helpers live in `lib/onboarding.ts` (unit-tested).
- **Import step reuses the Settings import**: the state machine + phase UI were extracted to `components/web/twitch-import/` (`useTwitchImport` + `TwitchImportPhaseView`); `TwitchImportButton` (Settings) is now a thin modal wrapper around them. Both talk to the `import-twitch-follows` edge function (fetch/import, 20 new streamers/day).
- **Twitch OAuth now requests `user:read:follows`** (`lib/twitch-scopes.ts`, used by the login server action and `lib/web/twitchConnect.ts`). Without it the provider token can't read follows — the import silently loaded ZERO follows before this fix. The callback validates the captured token against `id.twitch.tv/oauth2/validate` (must be a Twitch token WITH that scope) so a Google `provider_token` of a multi-identity account is never stashed as `twitchProviderToken`; on validate network failure it falls back to the old `app_metadata.provider === 'twitch'` heuristic.
- **"Connect Twitch" is a standalone Twitch OAuth token flow — NOT Supabase identity linking** (`lib/web/twitchConnect.ts` → `startTwitchFollowImport`). It runs Twitch's own implicit grant (`id.twitch.tv/oauth2/authorize?response_type=token`, `user:read:follows`) and returns to the page `/auth/twitch-import` (`app/[locale]/auth/twitch-import/`, like `/auth/login` — a `'use client'` body wrapped by the root layout; middleware rewrites the unprefixed URL into the English tree, and the token fragment never reaches the server), which reads the token from the URL fragment client-side, verifies the CSRF `state` we stashed in sessionStorage, and stores it in the same `twitchProviderToken` localStorage slot the OAuth callback uses. `router.replace` bounces back to `?step=import` (token fragment dropped), where `useTwitchImport` auto-loads the follows.
  - **Why not `linkIdentity`/`signInWithOAuth`** (the pre-2026-07-25 approach): `linkIdentity` PERMANENTLY attaches the Twitch identity and fails `422: Identity is already linked to another user` for any Twitch account already tied to another ST account (i.e. anyone who ever used "Continue with Twitch") — so email/Google users could never import, and the error surfaced only as the generic "Connecting to Twitch failed" via the callback's provider-error branch. The token flow needs no identity link, so it works uniformly for email/Google/Twitch-first accounts and changes NOTHING about the ST session.
  - Requires `NEXT_PUBLIC_TWITCH_CLIENT_ID` (same value as the backend `TWITCH_CLIENT_ID` secret) + the `/auth/twitch-import` redirect URI registered in the Twitch dev console (prod + localhost) — see `.env.example`. Unset client ID → import buttons degrade to "pick manually". Pure return logic (`lib/web/twitchImportReturn.ts`) is unit-tested; provider errors / denials come back on `next` as `connect_error` (`access_denied`, `scope_denied`, …) with friendly copy + manual-pick fallback.
- **Pick step**: default grid = most-followed streamers via the Partner API (`listStreamers({ order: 'followers' })`, limit 24 — same source as `/api/search`, `is_hidden` filtered server-side, live badges via `getLiveStreamerIdSet`); the Discover RPC chain (`fetchInterestProfile` + `fetchDiscoverRecommendations`) is only the fallback when the Partner API fails or returns empty — the grid heading follows the source ("Most followed" / "Popular right now"). Plus debounced `/api/search`; cards toggle favorites immediately through `FavoritesProvider` (optimistic, idempotent) — Continue only navigates. Deliberate deviation from the app: skipping does NOT seed featured favorites (the feed has a proper empty state + "Popular right now" fallback).
- **No completion flag** (deviation from the app's AsyncStorage step persistence): auto-entry only ever happens right after signup, so a revisit-by-URL just shows the wizard again — harmless. Step state is URL-mirrored (`?step=`, history.replaceState) so refreshes and the Connect-Twitch round-trip resume the right step.
- Local E2E: dev-login loop + auth flags in `.env.development.local`; real Twitch OAuth is NOT locally testable without a Twitch app + registered localhost redirect URI. After deploying, smoke-test one fresh Twitch signup (lands on import with follows listed), one Google signup (choice → Connect Twitch → follows import onto the Google account), one email signup (confirm link → wizard → Connect Twitch → follows import). Regression to verify the collision fix: sign in with Twitch once (claims the identity), sign out, sign up with a DIFFERENT email, Connect Twitch to the SAME Twitch account → import must now succeed (previously "Connecting to Twitch failed").

# Game hub UX round (2026-07-23)

`/game/[slug]` invariants an agent must not accidentally undo:

- **Schedule density**: `GameDaySection` renders high/medium slots as full SlotCards and collapses low-confidence upcoming predictions into compact rows behind a closed `<details data-low-bucket>` (crawlable, no reasoning teasers — LOW copy is the weakest and must not get a full card again). Cancelled slots ALWAYS keep the full card. Split logic is pure in `lib/game-schedule.ts` (unit-tested).
- **Filters without payload duplication**: the schedule stays fully server-rendered; `ScheduleFilters` (client) receives it as `children` and toggles the `hidden` attribute on `li[data-slot]`/`section[data-day]`/`details[data-low-bucket]` markers. Do NOT convert the schedule into client props (200 slots would double into the flight payload). Known accepted staleness: DayNavBar/day-heading counts describe the unfiltered schedule.
- **Per-slot `.ics`**: `SlotIcsButton` reuses `lib/feed/ics.ts` (same UIDs as feed/Program exports) and renders as a SIBLING of the SlotCard link (absolute overlay / row-end) — never a nested interactive. Eligibility: upcoming + not cancelled (`isIcsExportable`).
- **Ranking table** reuses `buildGameRankingRows` (same view model as `/rankings/game/[slug]`): Next-stream cell via `NextStreamTime` deep-links `#day-<utc-date>` only when that day section renders (`renderedDayKeys` guard); Hours/28d column hidden on mobile.
- **Next-stream is category-AGNOSTIC** (fixed 2026-07-25): the "Next stream" column of the ranking table means "when is this streamer next live", NOT "next time they stream THIS game". It is fed by `getNextSlotByStreamer(ranked ids)` (no `category` filter) — NOT the category-filtered `upcomingSlots` used for the schedule/day sections. The old wiring blanked the cell for top-follower streamers whose next predicted stream is a different game (e.g. KaiCenat/xQc on `/game/just-chatting`, and most of `/game/counter-strike`). `buildGameRankingRows` still takes the slots as its `upcomingSlots` arg — just pass the unfiltered next-slot list. `GameRankingRow.nextCategory` carries the predicted game of that next slot (null for `slot_kind='cancelled'`), rendered as a muted line under the time.
- **Heatmap** (`StreamTimesHeatmap` + pure `lib/game-heatmap.ts`): data from `/v1/games?category=&include=hour_histogram` (168 UTC minutes cells, weekday 0 = Monday), fetched failure-isolated in the page loader — degrades to a hidden section against an older API. Measured (same build, same data, document over the wire): pool 12 = 33.5 KB gzipped, 300 = 49.1 KB, **500 = 57.5 KB**; DOM 902 → 1,112 elements and TBT 49 → 39 ms between the 12- and 300-card builds. **Lighthouse's `total-byte-weight` reports UNCOMPRESSED sizes** (it claimed +212 KiB for the 300 pool); measure the wire cost with `curl … | gzip -9 | wc -c` instead — the local `next start` already sends `Content-Encoding: gzip`.

# Icon sprite for per-card icons (2026-08-01)

`components/web/icons/IconSprite.tsx` holds five glyphs as `<symbol>`s — heart,
eye, bell, play, calendar-clock — mounted once per document by the root layout
(`IconSpriteDefs`, inert and zero-sized) and referenced by `Icon` as a two-node
`<svg><use href="#sti-…">`.

- **Only icons whose count scales with the DATA belong here.** The homepage
  shipped 174 copies of the eye glyph and 165 of the heart, ~390 bytes and four
  DOM nodes each; the sprite makes each ~200 bytes and two nodes. Chrome icons
  appear a handful of times per page — they stay plain `lucide-react` imports,
  where tree-shaking and readability win. Adding a glyph is only worth it above
  a few dozen instances per page: the defs block costs ~1.2 KB on the ~200
  prerendered pages that reference nothing (accepted; those are the low-traffic
  static pages).
- **Presentation attributes live on the referencing `<svg>`, never in the
  symbol**, which is why ONE heart symbol serves both the outlined and the
  filled favourite state. `Icon` spreads `...rest` after its defaults, so a
  caller can still override `fill`/`strokeWidth` (the clip card's solid play
  triangle does). Its defaults reproduce lucide's stroke styling exactly.
- **The symbols must be in the same document as the references.** A structural
  check worth re-running after touching the layout: every prerendered
  `.next/server/app/**.html` that contains a `<use href="#sti-…">` must also
  contain the matching `<symbol id>` (verified 2026-08-01 across 244 files, 37
  of them using the sprite, 2,021 references, zero dangling).
- Sized to zero via an inline style rather than `display:none` — that is the one
  sprite variant with a history of breaking `<use>` — and `href` is used without
  an `xlink:href` twin (SVG2, fine on every browser Next 16 targets).
- Not in the sprite and worth a look someday: the app-download QR code is a
  single 21.5 KB inline SVG, which after this round is the largest SVG on the
  homepage by a wide margin (and it is paid twice, markup + flight).

# Mobile UX round (2026-07-30)

A mobile audit at 390px found the same three defect families across many pages. These are the rules that came out of it — check them when touching any list, card row or overlay control.

- **`min-w-0` belongs on the GRID/FLEX ITEM, not just inside the row.** A grid item defaults to `min-width:auto`, so a `truncate` descendant stretches the whole track: `/live` was scrolling sideways at 1031px on a 390px viewport, and titles in "Recent streams" were cut mid-word because the ellipsis container was wider than the screen. An inner `min-w-0 flex-1` cannot fix that — the track already grew. Every `<li>` in a grid of cards needs `min-w-0`, and so does every flex row that pairs a `truncate` label with a badge.
- **Badges are `shrink-0`** (`components/web/Badges.tsx`). Flexbox otherwise shrinks the short unwrappable word (LIVE, Twitch) instead of the label that has somewhere to go. Badge font floor is 10px; the dense `sm` scale used to be 9px.
- **Touch targets: 44px, without moving the design.** Small overlay controls (favourite heart 32px, lineup bell 28px, header buttons 36px) keep their visual box and gain an invisible `::before` hit area via `touchTargetExpander` in `lib/ui/positioning.ts`. That helper only adds `relative` when the caller has NOT positioned the control: Tailwind emits all `position` utilities in one layer, so a blanket `relative` beat callers' `absolute` (equal specificity, stylesheet order decides) and overlay hearts/bells silently fell out of their corners. Chips that stand alone in a row grow for real (`min-h-11`) — the pseudo-element trick would make neighbours' hit areas overlap across an 8px gap. `--header-height` is a layout contract for every sticky offset: the header must never grow, so its controls always use the expander.
- **Day labels are decided against the VIEWER's date, not the server's UTC date.** The schedule is grouped into UTC days; between local midnight and UTC midnight "today UTC" and the reader's own today disagree, and the page used to label a section "Tomorrow" while the slot rows inside it said "Thu, Jul 30 · around 7pm your time". `components/web/DayLabel.tsx` renders the heading via `useSyncExternalStore` (server snapshot = the UTC-referenced string, so ISR HTML stays deterministic; client snapshot recomputes against `localDateKey()`). aria labels use `utcDateAbsoluteLabel` — never the relative word, which would contradict the hydrated heading.
- **`LocalTime` splits the clock from the zone name**: hour/minute follow the page language, the abbreviation is probed via `en-US`/`en-GB` and stays latinized. Passing `undefined` as the locale took the abbreviation from the BROWSER's locale, so a German-configured browser rendered "8:06 PM MESZ" on the English page.
- **Ranking tables freeze the primary metric** (`PRIMARY_STICKY` in `RankingTable.tsx`). Six columns cannot fit a 390px phone at any width, and the ranked-by number was the column falling off the right edge — "39.7K" read as "39.7", a wrong number rather than a truncated one. Scrollbars stay visible on data tables (they are the scroll affordance) and hidden on decorative chip rails.
- **`/live` carries a `<details>` jump index** (`components/web/live/LiveJumpNav.tsx`) because the page runs to dozens of category sections and ~24,000px. Chips are server-rendered anchors (works with JS off); the client island exists only to close the panel on tap, since a sticky open panel would cover the heading it just scrolled to. Sections need `scroll-mt-32` to clear header + jump bar.
- **The locale banner hides its sentence below `sm`** instead of truncating it: at 390px there is room for ~20 characters next to the CTA, and a cut-off word says less than the CTA already does. The full sentence remains the region's `aria-label`.
- Chrome that must stay locale-aware: `HeaderUserMenu` (label + `localeHref`), `FloatingGetAppButton` (label + `localeHref`, and its hide-on-`/auth` check runs through `stripLocaleFromPath` — plain `startsWith('/auth')` only matched the English tree). The game hub is deliberately left English-only until M22 P4 localizes it as one piece; do not half-localize it.

# Phone-first CTA round (2026-07-31)

The 2026-07-30 audit ran at 390px. Re-running it at **320px** — the narrowest
screen the site claims to support — found the CTAs stacking and the document
itself scrolling sideways in five locales. Rules that came out of it:

- **A CTA pair belongs side by side on a phone, not stacked.** Both homepage
  conversion blocks now put their two buttons in one row below `sm` and let
  them split the width (`flex-1`), with reduced type/padding; from `sm` up they
  return to their original metrics and natural width. `min-h-11` keeps the 44pt
  target when a label stays on one line, and the row's default stretch keeps
  both boxes identical when one wraps to two. Sizing is dimensioned against the
  LONGEST localized label, not the English one: "Zaloguj się w przeglądarce"
  (pl) and "Завантажити застосунок" (uk) are the ones to test.
- **Give both buttons of a pair the same border, colour it per skin.**
  `flex-basis: 0` resolves against the border box, so a ring on only the
  outlined one makes it 2px wider than the filled one. And never put the colour
  in the shared class: two colour utilities on one element are resolved by
  STYLESHEET order, not class order, so a base `border-transparent` silently
  wins over the caller's `border-accent-cyan` — the outlined button loses its
  ring on desktop while the phone layout looks fine.
- **`min-w-0` has to be released at EVERY grid level, not just the outer one**
  (extends the 2026-07-30 rule). `HomeMostWatched` nests a grid of columns
  inside a grid of rows; releasing only the column left the row overflowing its
  column, and the page still scrolled sideways. Symptom to recognize: the auto
  track is wider than its own container (`grid-template-columns: 309px` on a
  272px box).
- **A label next to a badge needs a container query, not a breakpoint**, when
  the label is one unbreakable localized word. `SlotCard`'s "Confidence:" is
  134px in pl inside a 124px text column; it now renders only from
  `@min-[13rem]` of the COLUMN (`@container` on the text column), because the
  same card sits in a narrower cell on the Program page where a viewport
  breakpoint would guess wrong.
- **The header row has no slack at 320px**: brand, sign-in button and hamburger
  are all `shrink-0`, so only the gaps are left to give (`gap-2` below 360px)
  and the brand drops to `text-sm` there. The search field additionally steps
  out below 360px **only when the sign-in button is rendered**
  (`max-[359px]:[&:has(~[data-signin])]:hidden`) — squeezed to 9px it stopped
  being a search box and its absolutely positioned magnifier spilled over the
  neighbour, but without that button (today's production stealth state) it
  still gets ~130px and stays usable. Keep the `data-signin` attribute on the
  sign-in link if you touch `HeaderUserMenu`.
- **The end cap is a 2-column grid**, photo beside the copy from the smallest
  screen up; only the CTA cell moves (full width on a phone so the two store
  badges fit next to each other, back under the copy from `sm`). `.store-badge`
  scales every box metric with the viewport below 640px and floors at a width
  that fits 320px with the longest localized sub-label.
- **Regression check that catches all of this in one number**:
  `document.documentElement.scrollWidth === window.innerWidth` at 320px, for
  every locale. It was 357 (pl), 333 (de/es/pt), 330 (ru), 326 (fr) before.

## Header search: icon below `lg` (2026-07-31, second pass)

The header row is brand + search + nav pills + sign-in + hamburger, and the
search was the ONLY flexible item in it — so it silently absorbed every
shortfall: 22px wide on a 320px phone (es), 48px on an iPad in portrait. Below
`lg` it is now a 36px icon (`SearchBar` prop `collapsible`) that opens a fixed
panel under the header.

- **One input, three wrapper states** (`hidden` / fixed panel / inline field).
  Do not "solve" this by rendering a second input for mobile — the dropdown
  anchors to the wrapper and the query state would fork. `expanded` is false on
  the server, so the static HTML is the collapsed header.
- **The whole caller className is `lg:`-prefixed** (`lg:ml-auto lg:w-full …`).
  Below `lg` the wrapper is `fixed inset-x-3`, and a `w-full` there would
  over-constrain it against the insets.
- **Everything in the phone row is now shrink-0** — that is the consequence
  people trip over. The gaps and the brand size are the only give left, hence
  `gap-2` + brand `text-sm` up to `sm`. Adding any further fixed-width control
  to the header means re-measuring all 12 locales at 320/360.
- **Nav pills are `whitespace-nowrap`**: they are a fixed 36px tall, so a row
  1px over budget wraps a two-word label into a second line that overflows the
  pill — it does not read as "tight", it reads as broken.
- **Get-App is `lg:`, not `md:`** — the widest label in the row ("Скачать
  приложение" 174px, "Завантажити застосунок" 203px). The floating Get-App
  button covers that intent below `lg`.
- Below 360px the icon still steps out while a sign-in button is rendered
  (`max-[359px]:[&:has(~[data-signin])]:hidden`) — four fixed controls do not
  fit a 320px screen in any locale that spells sign-in out.
- **Exactly ONE `ml-auto` in the header row.** A flex row splits its free space
  between two auto margins, so a second one (it was on the hamburger wrapper)
  pins that control to the edge and strands everything before it mid-row. The
  margin lives on the search button; below 360px, where that button hides, the
  sign-in link carries it (`max-[359px]:ml-auto` in `HeaderUserMenu`). If you
  add a control, do not give it its own auto margin.

## `--header-height` is the OUTER height, in two tiers (2026-07-31)

`:root { --header-height: 57px }` + `65px` from `lg`, **including the 1px
bottom border** — every `top-[var(--header-height)]` sub-nav aligns to that
edge and every `scroll-mt-[calc(var(--header-height)+…)]` anchor clears it.

- It was a flat 56px until this round, i.e. 1px short on a phone and **9px
  short on a desktop** (the search input is 44px tall, the mobile controls
  36px). Every sticky sub-nav — home section nav, /live jump nav, program time
  bar, feed chips — parked that far UNDER the header, and jump targets landed
  behind the pinned bar. Nothing errored; it just looked slightly wrong.
- **The header row's height is pinned (`h-14 lg:h-16`), not derived from its
  content.** Change one and you must change the other. A control taller than
  the row now overflows visibly instead of silently desynchronising every
  sub-nav on the site — that is the point of pinning it.
- Regression check: scroll until a sub-nav pins, then
  `header.getBoundingClientRect().bottom - subnav.getBoundingClientRect().top`
  must be 0. Disable `scroll-behavior: smooth` first (globals.css sets it on
  `html`) or the measurement runs mid-animation and reads nonsense.
- **Every sticky bar carries the header's full translucency recipe**:
  `bg-background/95 backdrop-blur supports-[backdrop-filter]:bg-background/80`.
  The `/95` alone is only the no-backdrop-filter fallback — five bars shipped
  with just that and rendered at 0.95 alpha under a 0.80 header, which reads as
  a darker block glued below it rather than one continuous chrome layer.
- The chips inside those bars deliberately do NOT match the header's nav pills:
  same background, text colour, border and padding, but 44px tall / pill /
  12px text vs 36px / `rounded-lg` / 14px. The height is the standalone-chip
  touch-target rule from the 2026-07-30 round — do not "fix" it to h-9.

Two facts learned on the way: (1) the Next data cache keys a fetch by URL, not by `revalidate` — all callers share one entry and each applies its own staleness rule, the parameter only moves the ROUTE cap; (2) `getLiveStreamerIdSet()` has a 60 s process-local memo, and when that hits no fetch runs, so before the fix the affected routes flipped between a 60 s and a 300 s TTL depending on lambda warmth.
- **`/api/revalidate` purge is locale-SCOPED since 2026-09-05 (W2.1)**: the backend sends `{slug, langs: ['en', <streamer language>]}` and only those locale variants (+ the bare path, + `/wiki` per purged locale) are invalidated; the other ~10 locale variants age out over the normal 1800 s TTL. Rationale: every purge previously invalidated all 12 locale trees AND their data-cache entries, so each of the ~1,100 daily purge events re-rendered + re-fetched 12 variants of which 11 are barely read — measured as 40 % of ALL ISR write units and 69 % of all origin API fetches. Contract: `'en'` is always purged (the Google Indexing ping names the unprefixed URL → rewritten to `/en`); `langs` absent/non-array → full purge (backward compatible, and what generate-wiki-profiles sends on purpose — wiki edits change every locale). Sender: `supabase/functions/_shared/google-indexing.ts` (`REVALIDATE_LOCALES` must stay in sync with `UI_LANGS`). Decision + traffic basis (72 % en, 9 % de, 7 % ja): user call 2026-09-05.
- **Homepage discover sample is bucket-seeded, not `Math.random`** (W2.2, 2026-09-05): `sampleRandom(pool, 12, seededRandom(Math.floor(Date.now() / BUCKET_MS)))` in `app/[locale]/page.tsx` + sorted ids in `getNextSlotByStreamer`. The sample (and with it the next-slot fetch URL) is identical for all locale regenerations inside a 5-minute bucket, so the tail fetch shares ONE data-cache entry instead of missing per regeneration (was ~3,300 uncacheable `/v1/schedules` calls/day); rotation still happens every bucket. If you touch the discover block, keep seed and fetch-window on the SAME `BUCKET_MS` anchor (exported from `lib/server/next-streams.ts`).
- **Fetch keys built from the raw clock are the same bug in a different coat.** `app/[locale]/live/page.tsx` built `from`/`to` from a millisecond-precise `new Date()` until 2026-08-29, so every regeneration of every one of the 12 locales fired its own uncached sweep at a 60 s TTL. It now floors through `floorToBucket` like the homepage; the raw `now` still drives status decisions. (The file is treated as binary by git's heuristic — see the merge note below — but it contains no NUL byte and ripgrep reads it fine.)
- **Public pages must not read `searchParams`/`cookies()`/`headers()`.** `/app` read `searchParams.from` for one optional hint line and was therefore `private, no-store` — a function render per visit AND per link prefetch (615 in 28 h). The hint now lives in the client island `components/web/AppIntentBanner.tsx` (`useSearchParams` inside `<Suspense>`), the page is static with `revalidate = 3600`.
- **`prefetch={false}` on links to force-dynamic pages.** `<Link>` prefetches viewport links on every render; a prefetch of `/auth/login` is a full function invocation plus a GoTrue round trip (1,092 in 28 h, for a page almost nobody opened). The masthead login CTA, the header sign-in link, the signed-in menu links (`/feed`, `/program`, `/favorites`, `/settings`) and the "back to sign in" links carry `prefetch={false}`; keep it on any new link whose target is `force-dynamic` or auth-gated. Static targets (`/app`, hubs) may keep the default.

# Regions: functions in Dublin, Edge Functions pinned to eu-west-1 (2026-08-29)

The project's Postgres lives in **eu-west-1 (Dublin)**. Until 2026-08-29 the Vercel functions ran in `iad1` (Vercel's default), and Supabase Edge Functions run wherever the CALLER is — so every Partner API call executed in `us-east-1` and paid 3–5 transatlantic database round trips. Measured on the same code path: **390 ms in us-east-1 vs 122 ms in eu-west-1**; `/api/health` (one `listStreamers limit=1`) measured 374–479 ms inside the function. Two changes, both load-bearing:

- **`vercel.json` `regions: ["dub1"]`** — the Vercel function region (ISR regeneration, dynamic pages, API routes, OG images). It overrides the dashboard setting; Routing Middleware stays global regardless. Failover regions are Enterprise-only, so a Dublin outage means the functions are down — but so is the database, which is why one region is the right call. Regional pricing: dub1 line items run ~20 % above iad1 (ISR writes $4.80 vs $4.00 per 1M units).
- **Edge Function calls are pinned to `eu-west-1`** (`lib/supabase/region.ts`): the server-side Partner API client sends the `x-region` header (`lib/server/partner-api/client.ts`), browser callers append `?forceFunctionRegion=eu-west-1` via `functionsUrl()` in `lib/web/streamerSearch.ts` (search-streamers, add-streamer, import-twitch-follows, delete-account). The query parameter exists because the functions' CORS allow-list is `authorization, x-client-info, apikey, content-type` — a custom header would fail the preflight; the gateway reads the parameter before the function runs. PostgREST calls (`lib/server/anon-rest.ts`, feed events) are unaffected — they never touch an Edge Function. A pinned request is NOT re-routed when eu-west-1 is down (Supabase docs); acceptable, see above. Verify with the `x-sb-edge-region` response header. The mobile app pins the same way (`src/services/edgeFunctions.ts` in the StreamHub repo).

# OG image routes under `[locale]` MUST export `generateImageMetadata` (2026-08-29)

An `opengraph-image.tsx` inside the dynamic `[locale]` segment is only ISR-cached when it exports **both** `revalidate` and `generateImageMetadata` (one entry, `id: 'og'`; the route then lives at `…/opengraph-image/[__metadata_id__]`). With `revalidate` alone — or nothing — Next renders it per request: the streamer OG route ran Satori on every hit, 1,943 uncached renders in 28 h = 7.6 % of all function invocations, each with a Partner API call. Verified in production on 2026-08-29: the game and insights OG routes (which had the pattern) went MISS → HIT, every route without it stayed MISS on repeated fetches. All routes were converted that day; copy the block from `app/[locale]/game/[slug]/opengraph-image.tsx` (guard the empty-params build probe) for any new one, and check `x-vercel-cache` after the deploy.

**Second half of the fix (2026-08-30): pass `headers: ogCacheHeaders(revalidate)` to every `new ImageResponse(...)`.** Next records no `fallbackRevalidate` for these `[__metadata_id__]` routes in the prerender manifest and emits no `s-maxage` on their responses (`cache-control: public, max-age=0, must-revalidate`), so Vercel had no TTL for the cached entry and re-rendered it in the background every few seconds under traffic — measured on production for the already-"cached" game OG: HIT at age 2, STALE at age 4, HIT at age 1, STALE at age 3 … i.e. one Satori render per ~4 s per URL, while `next start` locally kept the entry HIT for the full TTL. `ogCacheHeaders()` in `lib/og/frame.tsx` emits `s-maxage=<revalidate>, stale-while-revalidate=<24×>`; Next stores the headers in the ISR entry and Vercel honours them. Keep the value equal to the route's `revalidate` export (the leaderboard helper carries its own `LEADERBOARD_OG_REVALIDATE = 300` for that reason).

# Remote images: request the size we render (2026-08-02)

Every avatar and stream thumbnail renders through `next/image` with
`unoptimized`, so **whatever the API stored is exactly what the browser
downloads** — no srcset, no resizing, no format conversion. Both upstream APIs
store their LARGEST variant (YouTube `=s800`, Twitch `-300x300`), and those were
being painted into 28–64px circles.

`lib/format/image-size.ts` rewrites the URL at RENDER time — never before
storing, so the stored URL stays the canonical largest one and a future layout
that needs a bigger avatar just asks for a bigger size.

- `sizedAvatarUrl(url, cssPx)` — YouTube: replace everything from the first `=`
  with `=s<N>-c-k-c0x00ffffff-no-rj`. Twitch: snap to the FIXED buckets
  28/50/70/150/300/600, because an arbitrary size 404s on `jtv_user_pictures`
  (unlike the two paths below).
- `sizedCdnImageUrl(url, cssWidth)` — live previews (`previews-ttv/…-440x248.jpg`)
  and box art (`ttv-boxart/…-285x380.jpg`), whose paths take ARBITRARY sizes.
  Aspect ratio is preserved from the stored URL.
- `cssPx` is the CSS size of the box, NOT a device-pixel guess: the helper
  applies the 2× DPR headroom itself, so every call site states the same thing.
  For a `fill` image, pass the largest entry of its `sizes` prop.
- **Never upscale** — the cap is not a nicety. Without it an avatar rendered
  into a wide box (the blurred thumbnail fallback asks for ~268px) resolves to
  Twitch's 600x600 bucket, which is 298 KB against the stored 112 KB: the
  helper would have made pages BIGGER. Unknown hosts are returned unchanged, so
  a new CDN degrades to today's behaviour rather than to a broken URL.

**Do NOT "fix" this by dropping `unoptimized`.** `GameBoxArt` is the one
deliberate exception (small closed set, stable URLs → the optimizer cache hits
almost every time, see the comment there); avatars and stream thumbnails change
per stream and would churn that cache for no gain. That is also why `/games`
was the only page in the survey with zero waste.

Measured before the change (14 page types, cold cache, CDP): 17.4 MB of images,
**15.7 MB of it pixels no screen could resolve**. Worst pages were `/streamers`
(4.36 MB images), `/rankings/most-followed` (3.18 MB) and `/live` (3.10 MB) —
all list pages, i.e. the waste scaled with the row count. Contract-checked
against 1,175 live production URLs before shipping: **−85.6 % on the rewritten
ones, zero 404s, none bigger.**

`/live` was the third-worst page and was invisible to every code search:
`app/[locale]/live/page.tsx` contains a stray NUL byte, so ripgrep classifies it
as binary and silently skips it. It is the only such file in the repo — if a
site-wide sweep ever comes up suspiciously clean, check for that.

# Vercel WAF & Bot Protection (2026-08-18)

The Vercel firewall carries the anti-crawl defenses against the residential-proxy botnet that impersonates browsers and drove the ISR-write bills (identified 2026-08-17, fingerprints rotated 2026-08-18). Config is managed via API (`VERCEL_TOKEN` in `.env.local`; GET/PUT/PATCH `api.vercel.com/v1/security/firewall/config?teamId=&projectId=`), current state (config v10):

- **Managed ruleset `bot_protection` = CHALLENGE** (since 2026-08-18; log mode 17.–18.08. for verification). Challenges every request Vercel classifies as a non-browser source, excluding its verified-bots list. The 30h log-mode evaluation showed: 33k flagged requests/day, 100% with empty `bot_name` — the impersonation crawler plus generic scripts; zero named bots (Google/Bing/AI crawlers/Discordbot all untouched), so the "don't block training bots" decision holds. A challenged request gets **HTTP 429 + `X-Vercel-Mitigated: challenge`** and never reaches Next.js (no ISR write, no function invocation).
- **Custom rule 0: `Bypass revalidate purge (server-to-server)`** — action `bypass`, condition path `eq /api/revalidate`. The on-demand purge (Supabase edge functions: generate-predictions + live/offline flips) is a Deno `fetch` = non-browser and MUST skip bot protection; the call is fire-and-forget (`EdgeRuntime.waitUntil`), so without the bypass it dies **silently** and predictions hang in the 1800s streamer-page TTL. **If `/api/revalidate` is ever renamed or moved, update this WAF rule in the same change.** The route still enforces `REVALIDATE_SECRET` itself — the bypass only skips the firewall, not auth.
- **Custom rule 1: `Challenge fake-browser crawler (JA4)`** — the two log-mode-verified fingerprints from 2026-08-17 plus three rotated ones added 2026-08-23 (config v12). Kept alongside bot protection on purpose: per-request bot classification catches only part of the crawler's traffic (~half on 2026-08-18, and the 21.08. generation carried NO `bot_category` at all — it executed JavaScript and produced 66% of all Web-Analytics pageview beacons), a listed JA4 is caught 100%. **Since 2026-08-23 this rule is AUTO-MANAGED by the StreamHub edge function `waf-autotune`** (hourly; started in log mode = mail-only, `WAF_AUTOTUNE_MODE=apply` makes it patch): it adds digests that were challenged ≥1000×/24h, never completed a verification (0 × HTTP 202 — the "cannot solve challenges, therefore no humans" proof) and are ≥95% unclassified, and expires digests silent for 30 days. **Since 2026-08-27 every managed group is `ja4_digest eq <digest> AND geo_as_number neq 8075`** (Microsoft; `WAF_AUTOTUNE_EXEMPT_ASNS` on Supabase): the rotation-#2 digest `…_d8a2da3f94cd` listed by hand on 23.08. turned out to be the fingerprint of Bing's headless-Chromium renderer too — verified `bingbot` was challenged 170/170 times in 48 h (JS chunks, whole streamer pages) while the crawler on the same digest was caught 20 %. Google was never affected. A JA4 digest identifies a TLS stack, not a client; the automation's `search_engine_traffic` gate would have refused that digest — the hole was the hand-listing. Prefer letting the function add digests; if you must hand-list, use the two-condition form (a lone `ja4_digest eq` group is still recognised, but reported as `migrate` and rewritten on the next apply run). Hand edits are otherwise safe — the function preserves every condition group it does not understand — but **do not rename the rule** (it is found by name) and do not `PUT` the config (regenerates rule ids). The manual override for a false positive is the `WAF_AUTOTUNE_ALLOWLIST` secret on Supabase, not a dashboard edit (the next run would re-add it). Diagnosis by hand still works via the Observability query API (`POST /v2/observability/query`, groupBy `client_ja4_digest` × `http_status` / `bot_category`; `filters` are silently ignored) — and the same rule applies: **no fingerprint without purity evidence**, JA4 digests are shared by real browsers of the same build (`t13d1516h2_8daaf6152771_*` IS ordinary Chrome except for the third segment), which is exactly why the automation insists on the 202-based proof.
- **API traps** (all hit on 2026-08-18): the public PATCH `rules.insert`/`rules.update` variants only accept `deny|challenge|log` — a bypass rule can ONLY be created via **PUT of the full config**. A PUT **regenerates every custom rule id** (the Observability `waf_rule_id` series restart under the new ids) and resets anything it doesn't carry. The CRS block (`gen`/`rce`/`xss`/`sqli` were `active, log` since setup) was lost that way and CANNOT be restored: "OWASP Core Ruleset is not available for this plan" — those flags were inert config that never fired a rule; no loss, don't try to bring them back.
- **Non-browser side effects:** `scripts/prod-selftest.local.mjs` (node fetch) may get 429-challenged — see the note in its header (temporary log-mode flip or Chrome DevTools MCP; never a bypass rule for gated pages). Social-preview bots (Discordbot/Twitterbot) carry a `bot_name` and were never in the flagged set.

# Supabase browser client is lazy (2026-08-29)

`lib/supabase/client.ts` no longer imports `@supabase/ssr` statically. The providers in the root layout used to construct the client during render on every page, which put the whole supabase-js bundle (GoTrue + Realtime + Storage, 238 KB raw / 62 KB gzip, ~25 % of the JS per page) into every route — for anonymous visitors, who never make a Supabase request. Rules:

- `getSupabaseBrowserClient()` (Promise, dynamic `import()`) is the only entry point for anything rendered on public/ISR pages: `AuthProvider`, `FavoritesProvider`, `FollowGameButton`. `AuthProvider` subscribes to `onAuthStateChange` only when `hasSupabaseAuthCookie()` sees an `sb-*` cookie (the @supabase/ssr auth cookie is not HttpOnly; same prefix rule as the middleware) and re-checks on `usePathname()` changes. Anonymous visitors stay `user = null` without loading anything — exactly what a cookie-less `INITIAL_SESSION` produced before.
- `lib/supabase/client-eager.ts` keeps the synchronous `createSupabaseBrowserClient()` for components that only exist on auth-gated or query-dependent pages (feed, program, settings, onboarding, the auth forms, /search hooks). Importing it statically pulls the chunk into that route — fine there, never on a public page. Both entry points return the same instance (`@supabase/ssr` caches the browser client internally).
- Sign-in and sign-out end in hard navigations (`window.location.assign`), so the mount-time cookie check is sufficient; the pathname re-check is insurance for a future soft-navigation login.

# Middleware session-refresh budget (2026-07-28)

`updateSession()` (`lib/supabase/middleware-helper.ts`) runs in front of EVERY request, so its failure mode is site-wide, not auth-local. On 2026-07-26/27/28 a swapping Supabase instance made GoTrue answer in tens of seconds and Vercel killed the edge middleware — **504 `MIDDLEWARE_INVOCATION_TIMEOUT` on ordinary pages, for logged-in visitors only**. Invariants that keep that from recurring:

- **Anonymous requests must never touch Supabase.** The `sb-*` cookie prefix check returns before the client is constructed. All SEO traffic depends on this — it is why anonymous visitors saw a healthy site throughout the incident. Do not move work above that check.
- **Passthrough paths skip the refresh entirely** (2026-08-29): `isPassthrough()` (`/api/*`, `/get`, the `/auth/callback|confirm|sign-out` route handlers, any dotted path) is checked BEFORE `updateSession()`. None of those render a server component that reads the session, and the auth handlers build their own server client; a signed-in visitor's `/api/search` keystrokes and sitemap fetches no longer cost a GoTrue round trip each. Their token is refreshed on the next page navigation.
- **The refresh is bounded by `SESSION_REFRESH_BUDGET_MS` (2.5s).** A healthy round trip measured ~100ms from Vercel (A/B: anon median 61ms vs logged-in 160ms on `/live`), so the budget only fires when the backend is genuinely unwell.
- **One `AbortController` drives both halves, and both are required.** As a signal it cancels the in-flight GoTrue request; as a race participant it guarantees return. The signal ALONE is not enough: auth-js wraps an aborted fetch into a *retryable* error and keeps retrying with exponential backoff until `AUTO_REFRESH_TICK_DURATION_MS` (30s) — past the middleware limit. Never replace the race with "just an AbortSignal".
- **A timeout degrades, it does not log anyone out.** The existing cookies are forwarded untouched and the refresh retries on the next request. A `setAll` arriving after the budget cannot corrupt the returned response (it reassigns the local variable to a NEW `NextResponse`).
- **This does not rescue gated pages** — `/feed`, `/favorites`, `/program`, `/settings`, `/onboarding` and `/auth/*` call `getUser()` themselves and would still stall. Everything else (`/`, `/streamer/*`, `/game/*`, `/rankings/*`, `/live`) has no server-side auth call at all, so for those the middleware is the only Supabase touchpoint and bounding it is sufficient.

Frozen by `lib/supabase/__tests__/middleware-helper.test.ts`. Root cause of the incident was compute size, fixed separately (Micro → Small, 2026-07-28); the budget is the tier-independent guard.

# `/tonight` — the evening-intention hub (2026-08-05)

`/tonight` is the TV-magazine page: "who is streaming tonight", the recurring daily query that `/live` ("right now") does not serve. Sibling hub, same locale/index machinery, `revalidate = 300`. Pure core in `lib/tonight/logic.ts` (51 unit tests), island `components/web/tonight/TonightBlocks.tsx`, plus `PrimetimeCard` and the two `TonightLocal` scraps.

- **The reference-zone model is the whole design.** "Tonight" is local, and one prerendered page serves every timezone — the standing rule forbids deriving it from the render machine's clock. So each LOCALE has a fixed reference zone (`TONIGHT_REFERENCE_ZONES`: de → Europe/Berlin, ja → Asia/Tokyo, pt → America/Sao_Paulo, en → Europe/London). A per-locale constant is not viewer-dependent, so it stays deterministic and cacheable. **Never replace it with a runtime clock or a header/cookie read.**
- **Blocks are ABSOLUTE instant ranges; their headings are only a clock reading.** That is what lets the island re-format each heading in the viewer's own zone after hydration without moving a single card between blocks — no reflow, no hydration mismatch. Verified over CDP `Emulation.setTimezoneOverride`: Berlin renders "Ab 18:00 … Alle Zeiten MESZ", Tokyo the same cards as "Ab 1:00 … Alle Zeiten in deiner Zeitzone", Los Angeles "Ab 9:00". Zero hydration warnings in all three. **If you ever make the blocks depend on the viewer, the cards must become client-rendered data — do not half-do it.**
- **Accepted limitation:** a viewer far from their locale's reference zone gets boundaries on odd local hours. Their evening is still inside the window (it is 12 h wide), only its edges shift. Full per-viewer re-windowing would mean shipping the whole pool as data; deliberately not done.
- **Broadcast-day convention** (`BROADCAST_DAY_START_HOUR = 6`): before 06:00 reference-local the page is still showing the night that started yesterday at 18:00 (`mode: 'night'`, its own H1), so it never promises an evening 17 hours away. The window is therefore never more than 24 h ahead — that bound is what makes `TONIGHT_FETCH_HOURS = 26` sufficient for every locale, and it is unit-tested across all 12 zones × 24 hours.
- **The fetch window is LOCALE-INDEPENDENT on purpose** (`now` → `now + 26 h`, bucketed): all 12 prerenders must hit the same URL or Next's data cache dedupes nothing and each runs its own sweep — the failure mode that aborted the 2026-07-27 deploy. The per-locale evening is cut out afterwards in pure code. Same rule for the OG image's count fetch.
- **One bucketed clock** drives the fetch window, the evening resolution AND the expiry cut, so a regeneration inside a 5-minute bucket is byte-identical (ISR writes are billed only on changed output). The editorial ranking breaks every tie on `id` for the same reason.
- **The prime-time highlights are REMOVED from the block listing.** The same card twice within one screen reads as a bug. Block counts + highlights therefore sum to the intro's total, not to the block counts alone.
- Highlight ranking uses the cached featured sweep (`fetchFeaturedStreamers`) as a follower prior — no new API surface. A failed sweep degrades to confidence-then-time ordering rather than an empty box. Cancelled and low-confidence slots never rank (the box is an editorial promise) but cancelled slots DO stay in the listing, struck through — "no stream tonight after all" is exactly what a listings page exists to say.
- A block a filter empties is `hidden` outright; an orphan heading reads as a loading bug. Filter chrome, match counter and reveal labels are REUSED from `homeFeed.liveFilter*` / `lineupShowMore` — only genuinely new wording lives in `HubLex.tonight`.
- **The "already live" opener has the homepage rail's filter pair, and its POOL is not its visible cut** (`TONIGHT_LIVE_CAP = 8` visible, `TONIGHT_LIVE_POOL_MAX = 200` searchable). The filter vocabulary is imported from `lib/home/live-rail.ts` verbatim (`buildLiveFilterItems` / `computeVisibleLiveIds` / `countLiveFilterOptions` / `matchesLiveFilters`), so the two surfaces can only disagree on purpose. Unfiltered = the first 8 rows, all server HTML, zero deferred nodes; ANY filter = every match in the pool, however deep it ranks. Verified in the browser with German seeded exclusively at ranks 15-20: resting shows none of them, picking German surfaces all of them out of the deferred payload. **Never let the rendered set become the filter scope** — that was the homepage rail's bug until 2026-07-29 (German offered 3 of 17 live streams, several languages had no option at all). `TonightLiveRow` is deliberately not `'use client'` so it compiles into both graphs (`LiveRailCard` precedent).
- Internal links: footer "Discover" column, `/live` footer cross-link, sitemap `hubEntries('/tonight')`, `llms.txt`. Deliberately NOT in the header nav — a 5th item does not survive the 320px budget.

# Localization (M22)

The D6 keying rule (applies to EVERY component and metadata builder):

- **UI/chrome strings follow the VIEWER's locale** — the `[locale]` route param, threaded as a prop or resolved from `params`. NEVER from cookies or `Accept-Language` (the `NEXT_LOCALE` cookie is client-only: banner + switcher highlight; a server read would fragment the CDN cache and break ISR — K1 class).
- **Content (bio, slot reasoning) follows the best available content language for that viewer**, always rendered with its OWN `lang`/`dir` attributes: `pickDescription(streamer, viewerLocale)` in `lib/seo.ts` (original on the streamer's own-language variant, `description_en ?? description` everywhere else) and `pickReasoning(slot, viewerLanguage)` in `lib/slot-copy.ts` (real copy when its `copy_language` is the viewer's or English; otherwise the always-English `generic_reasoning`, labelled via `SlotLex.autoSummary`).

Lexicon inventory (typed `Record<UiLang, …>` — a missing key/language is a compile error; every table has a vitest completeness + English byte-identity test): `lib/i18n-ui.ts` (streamer-page body, per-lang files `lib/i18n/ui/*.ts`), `lib/i18n-slot.ts` (client-safe slot chrome), `lib/i18n-chrome.ts` (header/footer/404), `lib/i18n-sitemeta.ts` (hub titles/descriptions), `lib/i18n-hub.ts` (hub BODY copy, per-lang files `lib/i18n/hub/*.ts`), `lib/i18n-banner.ts` (locale suggestion banner). English values are byte-identical to the pre-M22 inline strings — en pages must never change when a string moves into a lexicon.

Indexability matrix (P3, implemented in `applyLocaleSeo(meta, locale, path, indexableLocales)` — ALWAYS the last call in a `generateMetadata`):

- Hubs `/`, `/live`, `/streamers` (+ `/streamers/page/[n]`), `/games`, `/rankings`: `INDEXABLE_HUB_LOCALES` (`lib/seo.ts`). **S4.1 (2026-08-05): widened to every UI locale except `ar`** after GSC review #1 passed. `ar` is deliberately excluded — its chrome is translated but the document stays LTR with per-text-block `dir` only; the gate for adding it is the logical-properties migration (~52 files use physical left/right utilities). pt is pt-BR by register decision (S4.2), served under the generic `pt` hreflang.
- Sentence-final value rule (both directions): German compact numbers end with a period ("19,2 Mio.") AND ru/uk/hu date labels end with an abbreviation period ("2026 г." / "2026 р." / "aug. 5.") — a lexicon template must never place such a value before its own sentence period ("Mio..", "г.."). Guarded by vitest (i18n-hub: "freshness lines never double the period").
- `/streamer/[slug]`: `streamerIndexableLocales(streamer.language)` — en + own language when it's one of the 12; the thin-page gate inside `buildStreamerMetadata` wins for every variant (incoming `noindex` is never overridden and never gets a cluster).
- Game pages `/game/[slug]` + `/rankings/game/[slug]` (M22 P4, 2026-08-03): fully localized bodies (HubLex `game`/`gameRanking`/`gameChips` sections), indexable per `INDEXABLE_GAME_LOCALES` (`lib/seo.ts`, currently `['en','de']` — widened separately from the hubs). Their own thin gates (`isGameHubIndexable`, `isRankingIndexable`, pages >= 2) still win. Client components (GameRankingExplorer, ScheduleFilters, StreamTimesHeatmap, BestSlotChips, FollowGameButton) receive server-resolved label props — peak/score values only exist after the client timezone shift, so those labels are `{placeholder}` templates. Sitemap game entries are per-locale DISCOVERY entries WITHOUT alternates (proxy-gate rule, streamer-entry precedent). `/game/[slug]/best-time` stays en-only (M24).
- Everything else (leaderboards, games/[view], legal, /app, /developers): en-only (omit the 4th arg). Non-en variants are viewable but `noindex,follow` + self-canonical — NEVER a foreign canonical next to noindex.
- hreflang clusters (`alternates.languages` + `x-default` → unprefixed en) are emitted ONLY on indexable variants and list ONLY indexable variants; `app/sitemap.ts` mirrors them (one entry per indexable variant, each carrying the full cluster). A cluster needs ≥2 members or it is omitted entirely.
- No server-side locale redirects, ever (cloaking risk). `/en/*` → 308 unprefixed is the single exception (URL normalization, not negotiation).

GSC monitoring after any locale/index change (first review ~2 weeks post-deploy): (1) Settings → International Targeting / hreflang errors must stay at zero ("no return tags" = a cluster listing a noindexed variant); (2) Coverage: the /de hub pair + own-language streamer URLs should move to "Indexed" without a matching drop of their en twins (duplicate-cluster = matrix bug); (3) soft-404/duplicate spikes on `/de/*` mean body localization is too thin — pull the locale from `INDEXABLE_HUB_LOCALES` rather than shipping half-translated indexable pages; (4) URL-inspect one en+de hub pair and one en+own-language streamer pair for "Google-selected canonical = user-declared".
